# Plant Care UA — Prototype Specification

**Версія:** 0.1 · **Статус:** погоджений напрямок, завдання для Claude Code · **Мета:** робочий прототип за один вечір.

## 1. Мета та межі

Створити **публічно демонстрований, mobile-first вебпрототип українською** для догляду за кімнатними рослинами, садом, городом, деревами й кущами. Користувач має за кілька дій додати рослину, вибрати населений пункт, отримати базові рекомендації та бачити наступні завдання догляду. **Відсутність реєстрації та обов’язкових регулярних витрат** — вимога.

Це **демо/MVP-прототип, а не агрономічно сертифікований сервіс**. Не стверджувати, що прогноз поливу точний: показувати *орієнтовний час перевірки вологості ґрунту*, а не обов’язковий полив.

## 2. Погоджений дизайн

Гібрид **A + B + D**: природний світлий мінімалізм (A), інформативна панель саду й календаря (B), надшвидкий мобільний сценарій (D). Читабельна українська, великі фото, округлені картки, спокійна зелена палітра, контрастні кнопки; на смартфоні — зручна нижня навігація, на ПК — бічна/верхня. Не копіювати чужий UI. Головна CTA: **«Додати рослину»**.

### Екрани
1. **Головна:** місто, поточна погода/стан джерела даних, огляд колекції, найближчі завдання, швидке додавання.
2. **Мої рослини:** фільтри «Усі / Кімнатні / Сад / Город / Дерева й кущі», картки, пошук.
3. **Додати / редагувати:** ручний вибір із каталогу; фото з файлу/камери як вкладення, назва, категорія, тип розміщення, дата останнього поливу; необов’язкові поля розумного режиму.
4. **Деталі рослини:** фото, умови, підказка про наступну перевірку ґрунту, історія поливів, кнопка «Полив виконано» та «Перевірив ґрунт».
5. **Календар:** завдання сьогодні/найближчі, позначення виконаних.
6. **Налаштування:** населений пункт, експорт/імпорт резервної копії, пояснення роботи рекомендацій.

## 3. CORE: обов'язково працює

- Реальна навігація між екранами, адаптація під мобільний екран 390 px та десктоп 1280 px.
- Демо-каталог: щонайменше 12 рослин, репрезентативно з усіх 4 категорій; назви українською, базові поля догляду. Зберігати дані каталогу як локальний JSON/TS; **не вигадувати точні агрономічні нормативи**, позначати рекомендації як загальні, для прототипу.
- Додавання, редагування та видалення екземпляра рослини; підтвердження видалення.
- Фото: завантаження/камера через стандартний file input, локальний прев’ю. **Не обіцяти розпізнавання фото**, якщо Gemini не підключено.
- Вибір міста з прикладами **Київ, Львів, Одеса, Харків, Дніпро** (координати заздалегідь задані, не потрібен геолокаційний дозвіл). Місто зберігається на пристрої.
- Погода з Open-Meteo без ключа: температура та опади (за доступності також відносна вологість), зрозумілі одиниці виміру; timeout, індикація часу оновлення, кеш останньої відповіді, graceful fallback до локальних загальних рекомендацій при відсутності мережі. Перевірити актуальні умови використання до публічного/комерційного запуску.
- Два способи використання: **Простий** (мінімум полів) і **Розумний** (необов'язково: у приміщенні/на балконі/відкритий ґрунт, ґрунт, сонячність, горщик/ґрунт, за бажанням — вологість за ручною оцінкою). Не вимагати усіх полів.
- Детермінований базовий модуль підказок: різні шаблони для кімнатних та відкритого ґрунту; погода впливає переважно на **пріоритет перевірки** для вуличних рослин; показувати *«Перевірте вологість ґрунту»* і пояснювати чому. Не генерувати фіктивні літри води, точну дату або гарантію без даних про реальну вологість ґрунту.
- Журнал: запис факту поливу з датою, можливість скасувати помилковий запис. Завдання «перевірити ґрунт» вручну позначаються виконаними.
- Локальне зберігання **IndexedDB** (рекомендовано `idb`, або нативний IndexedDB); збереження колекції, журналу, налаштувань і фотографій із контролем розміру. Експорт/імпорт валідованого JSON з версією схеми; не перезаписувати дані без підтвердження.
- Accessibility: семантичні елементи, клавіатурна навігація, підписи полів, стан завантаження та помилок.

## 4. AI: окрема опціональна інтеграція

Архітектурний інтерфейс `PlantIdentificationProvider` з режимами `manual` (завжди доступний) та `gemini` (лише за наявності безпечного backend proxy). UI показує запропоновані варіанти **для підтвердження користувачем**, не оголошує AI-ідентифікацію безпомилковою.

**За один вечір:** реалізувати UI для завантаження фото та ручний пошук. Можна показати явний бейдж **«AI-розпізнавання — незабаром»** або локальний **деморежим, чітко позначений як імітація**. Не викликати Gemini без серверного захисту. НІКОЛИ не розміщувати спільний API-ключ у Vite env, фронтенді, git чи GitHub Pages. Якщо окремий захищений проксі вже є — можна підключити за залишкового часу, з rate limiting, обмеженням розміру файлу, валідацією запитів і квотами. Сам проксі не є блокером прототипу.

## 5. Технології

- **Vite + React + TypeScript**.
- **Tailwind CSS**, мінімум залежностей, за потреби `lucide-react` для іконок.
- **IndexedDB** для даних; `localStorage` дозволений лише для дрібних налаштувань.
- **Open-Meteo Forecast API** для погоди (перевірити схему й умови на https://open-meteo.com/).
- PWA: `manifest` + іконка, встановлення як додатку за можливості; **офлайн-стратегія — good, не блокер**.
- Не використовувати сервер, хмарну БД, платний SaaS, авторизацію, платний AI як обов'язкові залежності.

## 6. Не входить у прототип

Авторизація, синхронізація між пристроями, push-сповіщення при закритому браузері, діагностика хвороб, розпізнавання як обов’язкова функція, точні агрономічні розрахунки норми води, автоматичний графік добрив, планування грядок, production-grade серверна платформа, монетизація, повна мультимовність. Не витрачати час на ці функції до проходження приймальних сценаріїв.

## 7. Явна модель даних

`PlantCatalogEntry`: `id`, `commonNameUk`, `category`, `careSummary`, `lightHint`, `soilHint`, `wateringHint`.

`UserPlant`: `id`, `catalogId`, `customName?`, `category`, `placement` (`indoor|balcony|outdoor|greenhouse`), `cityId`, `imageBlob?`, `addedAt`, `soilType?`, `sunExposure?`, `potOrGround?`.

`CareEvent`: `id`, `plantId`, `type` (`watered|soil_checked`), `timestamp`, `note?`.

`Settings`: `schemaVersion`, `selectedCityId`, `mode` (`simple|smart`).

Зберігати ISO timestamps; не змішувати локальний час із UTC без явного форматування. Резервна копія повинна містити дані про рослини та історію; фото або експортувати з обмеженнями розміру, або **чесно попереджати**, що вони не включені (рекомендовано включити після зменшення зображень).

## 8. План виконання для Claude Code

**Крок 1 — Scaffold.** Створити проєкт, встановити лише необхідні залежності, налаштувати TypeScript і базову структуру.

**Крок 2 — UI.** Головна, колекція, форма рослини, деталі, календар, налаштування, мокові демодані. Використати узгоджений A+B+D.

**Крок 3 — Дані.** IndexedDB, CRUD, журнал, експорт/імпорт.

**Крок 4 — Погода та логіка.** Open-Meteo, кеш/помилки, прозорі підказки залежно від умов; без помилкових обіцянок точності.

**Крок 5 — Тестування.** Smoke через Playwright (або доступний браузерний інструмент), прогнати ширину 390/1280; перевірити перезапуск, offline/fallback, імпорт/експорт, порожню колекцію, помилки вводу.

**Крок 6 — Handoff.** `README.md` з командами запуску, список реалізованих/нереалізованих функцій, відомі обмеження, демо-інструкція. Якщо є Git, зробити чистий коміт після успішних перевірок; не пушити без налаштованого remote/дозволу.

## 9. Критерії готовності

- `npm install` та `npm run dev` успішні; `npm run build` проходить без TypeScript-помилок.
- Користувач може додати кімнатну рослину і городню культуру через ручний каталог; обидві залишаються після перезавантаження.
- Зміна Київ → Одеса змінює дані про погоду або явно показує стан недоступності API; немає фальшивих погодних даних без маркування «демо».
- Видно рекомендацію щодо **перевірки** вологості ґрунту з поясненням застосованих факторів.
- «Полив виконано» додає запис у журнал; можна скасувати помилковий запис.
- Експорт і повторний імпорт повертають колекцію та історію без втрати ключових даних; некоректний файл не руйнує локальні дані.
- На мобільному 390 px немає горизонтального переповнення, основні кнопки легко натискати.
- Відсутні відкриті API-ключі, відсутня обов'язкова реєстрація чи оплата.
- Не працюючі AI-функції чесно позначені як майбутні/демо, а не маскуються під справжню ідентифікацію.

## 10. Робочі інструкції Claude Code

Використай **Frontend Design**, якщо він доступний в інсталяції; Playwright MCP — якщо доступний; Git — звичайними командами. **Не блокуй початок роботи, якщо плагіни не встановлені:** реалізуй і тестуй наявними засобами. Не витрачай час на встановлення десятків скілів. Обирай найпростіше робоче рішення, а не масштабовану платформу на майбутнє. Виконуй кроки послідовно й самостійно виправляй знайдені помилки. Після кожного етапу перевіряй запуск/збірку, не декларуй неперевірені функції як готові.

**Початковий запит для Claude Code:**

> Прочитай `PROTOTYPE_SPEC.md` і реалізуй робочий прототип згідно з ним. Працюй за етапами 1–6 без перепроєктування узгоджених рішень. Пріоритет — демонстраційний наскрізний сценарій, якісний mobile-first UI та реальна локальна працездатність. Не додавай обов'язкових платних залежностей і не винось секрети у фронтенд. Запускай build і smoke-тести, виправляй помилки, у фіналі дай короткий звіт: що працює, що залишено на потім і як запустити.
